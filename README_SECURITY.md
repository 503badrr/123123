# دليل أمن Switch

آخر مراجعة: 2026-08-03

## النطاق الأمني

هذا المستودع يشغّل متجر Switch على Cloudflare Worker `dark-disk-4155`، مع Supabase للمصادقة وقاعدة البيانات، وTap Payments كمسار الدفع الافتراضي. GitHub `main` هو مصدر الشفرة المعتمد، والنطاق النهائي هو `swwiitch.com` و`www.swwiitch.com`.

## تصنيف البيانات والأسرار

### قيم عامة مسموح بظهورها في المتصفح

- `VITE_PUBLIC_SITE_URL`
- `VITE_PUBLIC_API_URL`
- `VITE_SUPPORT_EMAIL`
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`
- مفاتيح النشر العامة التي يصرّح مزود الدفع صراحة بإرسالها للمتصفح

### أسرار خادمية فقط

- `SUPABASE_SERVICE_ROLE_KEY`
- `TAP_SECRET_KEY`
- أسرار Webhooks ومفاتيح Telr/Moyasar/HyperPay السرية
- `RESEND_API_KEY`
- `JWT_SECRET` و`SESSION_SECRET`
- مفاتيح Cloudflare API وGitHub tokens

لا تُحفظ الأسرار في GitHub أو Lovable chat أو screenshots أو متغيرات تبدأ بـ`VITE_`. يجب تدوير أي سر ظهر سابقًا في رسالة أو سجل.

## المصادقة والصلاحيات

- جلسات المستخدم تعتمد Supabase Auth.
- صفحات الإدارة تتطلب مستخدمًا مسجّلًا ثم تحقق دور `owner | admin | staff` وحالة `is_active=true`.
- التنفيذ الفعلي لفحص الإدارة موجود في `private.is_admin()` كدالة `SECURITY DEFINER` بلا مدخلات وتعتمد فقط على `auth.uid()`.
- `public.is_admin()` واجهة توافق `SECURITY INVOKER` لتفادي رفع الصلاحية من مخطط API العام.
- `PUBLIC` و`anon` لا يملكان تنفيذ دوال الإدارة.
- الجداول الحساسة محمية بـRLS، والجداول الخادمية `contact_messages` و`rate_limits` تملك سياسات deny صريحة لـ`anon` و`authenticated`؛ الوصول إليها يتم عبر service role داخل Server Functions فقط.

## ملاحظات Supabase Advisor المقبولة

ليست كل ملاحظة Advisor ثغرة. القرار يجب أن يعتمد على grants وRLS ومسار استخدام التطبيق.

- `products` و`site_banners` مقروءتان للعامة عمدًا لأنهما تغذيان واجهة المتجر. يجب أن تظل الكتابة محصورة بالإدارة.
- `orders`, `order_items`, `payments`, `profiles`, `notifications`, و`support_tickets` تحتاج `SELECT` لدور `authenticated` لكن RLS يقيّد كل مستخدم إلى صفوفه أو يتيح الإدارة فقط.
- `private.is_admin()` تظهر كملاحظة `SECURITY DEFINER` لأنها قابلة للتنفيذ من `authenticated`. هذا مقصود لتشغيل RLS، والدالة بلا معاملات وتعيد Boolean فقط بناءً على `auth.uid()`. أي تغيير في نص الدالة أو exposed schemas يتطلب مراجعة أمنية جديدة.
- تنبيه `Leaked Password Protection Disabled` لا يُحل عبر SQL؛ يجب تفعيله من Supabase Dashboard ضمن Auth password security قبل الإطلاق العام.
- تنبيهات `unused_index` لا تبرر حذف الفهارس في مشروع منخفض الحركة. يُراجع الاستخدام بعد وجود بيانات إنتاج كافية.

## الدفع وWebhooks

- لا تعتبر صفحة الرجوع `/success` دليلًا على نجاح الخصم.
- الحالة الموثوقة تأتي من Webhook موقّع أو استعلام خادمي موثق لدى مزود الدفع.
- يجب التحقق من توقيع Tap باستخدام `TAP_SECRET_KEY` ومقارنة ثابتة التوقيت.
- يستخدم `webhook_events` مفتاحًا فريدًا على `(provider, event_id)` لمنع المعالجة المكررة.
- لا يتم تسليم الكود الرقمي إلا بعد حالة دفع نهائية موثقة.
- لا تُسجل payloads التي تحتوي بيانات دفع حساسة أو أسرارًا كاملة.

## الأكواد الرقمية

- ترفع الأكواد الحقيقية من `/admin/codes` عبر CSV فقط.
- لا تلتزم ملفات CSV أو الأكواد في Git.
- الملف المقبول: `product_slug,code,expires_at,status`.
- صلاحية الرفع للإدارة فقط، وكل عملية استيراد تُكتب في `audit_logs`.
- اسم العمود `code_ciphertext` تاريخي؛ لا يُفترض أن القيمة مشفرة تشفيرًا قويًا لمجرد الاسم. حتى تنفيذ تشفير فعلي مع إدارة مفاتيح، تُعامل الأكواد كنصوص شديدة الحساسية وتُحصر في service role ولوحة الإدارة.
- يمنع إرسال الكود في logs أو analytics أو رسائل الخطأ.

## حماية واجهات الخادم

- جميع المدخلات تمر عبر Zod أو تحقق مكافئ.
- Rate limiting يفشل مغلقًا: تعطل مخزن الحد يمنع الطلب بدل السماح غير المحدود.
- عنوان IP يُخزن كـSHA-256 hash عند الحاجة، لا كنص خام.
- رسائل قاعدة البيانات الداخلية لا تُعاد للمستخدم؛ التفاصيل تذهب إلى logs الخادم فقط.
- CORS وallowed origins يجب أن تقتصر على النطاقين الرسميين وبيئات التطوير الموثقة.

## تدوير المفاتيح

عند الاشتباه بالتسريب:

1. عطّل أو دوّر المفتاح لدى المزود فورًا.
2. حدّث Cloudflare Worker secrets أو Supabase secrets.
3. لا تضع القيمة الجديدة في GitHub.
4. أعد النشر وافحص المسارات المتأثرة.
5. راجع Cloudflare Logs وSupabase Logs و`audit_logs` للفترة المشبوهة.
6. وثّق الحادث ووقت التدوير ومَن نفذه دون تسجيل السر نفسه.

## الاستجابة للحوادث

### SEV-1

اختراق حساب إداري، تسريب مفتاح دفع/service role، تسليم أكواد دون دفع، أو تعديل غير مصرّح للطلبات.

- أوقف checkout أو التسليم المتأثر.
- دوّر المفاتيح.
- احفظ الأدلة والسجلات.
- حدّد نطاق المستخدمين والطلبات المتأثرة.
- لا تعِد الخدمة قبل تحقق مستقل.

### SEV-2

فشل Webhook، ارتفاع أخطاء 5xx، أو توقف Supabase/Cloudflare مع عدم وجود دليل تسريب.

- فعّل وضع الصيانة عند الحاجة.
- أوقف retries المؤذية أو التسليم المتكرر.
- راقب الاستعادة ثم نفذ reconciliation للطلبات.
